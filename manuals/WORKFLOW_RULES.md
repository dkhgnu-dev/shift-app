# Workflow Rules

## 起動時ルール

AIは作業前に以下を確認します。

1. 自分が開いているプロジェクトのルート。
2. `AGENTS.md` の指示。
3. `docs/handoff/CURRENT_STATUS.md` の現在状況。
4. `manuals/STARTUP_CHECKLIST.md`。
5. 存在する場合は `docs/PROJECT_RULES.md` と `docs/handoff/WORKFLOW_RULES.md`。
6. 必要なhandoffファイル。

`manuals/AI_TEAM_WORKFLOW.md` と `manuals/WORKFLOW_RULES.md` の全文は、詳細判断が必要な場合だけ追加で読みます。毎回の固定読み込みを増やさず、必要な情報だけを読むことを優先します。

## 新規プロジェクトの開始

新規プロジェクトでは、`CURRENT_STATUS.md` を Cycle 1 にして開始します。
別プロジェクトのhandoff履歴、提案、サイクル番号、固有ルールはコピーしません。

新規プロジェクトでは、実装に入る前に **P0 技術選定・作り方確認** を行います。
Kazumaxは「作りたいもの」「使う人」「困っていること」「失敗すると困ること」を伝えれば十分です。AIチーム側が、サーバー、DB、言語、フレームワーク、既存サービス利用の要否を確認し、最初の作り方を提案してください。

P0で確認すること:

- 見せるだけのサイトか、保存・計算・出力を行う業務ツールか。
- DB、ログイン、Excel/PDF出力、外部連携、複数人利用が必要か。
- 自分のPCだけで使うのか、本番公開やスマホ利用まで必要か。
- サーバーなし、サーバーあり、既存サービス利用のどれが一番ラクで安全か。
- 将来の修正や機能追加がしやすい構成か。
- Kazumaxが知らないことで損しそうな便利な選択肢がないか。

P0の内容は `docs/handoff/P1_Air_Blueprint/` または `docs/proposals/` に短く保存してください。
金額、DB、Excel、公式書類、保存処理などが絡む場合は、Airだけで決めずDexへ事前監査を回してください。

## 途中開始プロジェクトの棚卸

すでに「とりあえず作り始めた」プロジェクトで苦戦している場合は、いきなり作り直さず、まず途中棚卸を行います。
目的は、今ある努力を活かしながら、設計・技術選定・仕様のズレを見つけることです。

棚卸で確認すること:

- 最初に作りたかったものと、今できているものの差。
- 詰まりの原因が、仕様、UI、データ構造、計算ロジック、技術選定、検証不足のどれか。
- 今の構成が目的に合っているか。
- 捨てる部分、残す部分、作り直すより直した方がよい部分。
- 次に進むための最小サイクル。

シフト作成、予約管理、在庫管理、会計、補助金帳票のように、条件が多く保存や自動計算が必要なツールは、途中棚卸を優先してください。
Airは棚卸案を作り、危険度が高い場合や技術選定の見直しが必要な場合はDexへ回してください。

## 共通ルールと固有ルールの分離

- 共通ルール: `AGENTS.md`, `CLAUDE.md`, `.cursorrules`, `manuals/`
- 固有ルール: `docs/handoff/CURRENT_STATUS.md`, `docs/PROJECT_RULES.md`, `docs/handoff/WORKFLOW_RULES.md`
- 作業履歴: `docs/handoff/` 配下の各サイクルファイル
- 改善提案: `docs/proposals/`

## 編集前の確認

コードや設定を変更する前に、対象ファイル、目的、影響範囲を短く確認してください。
危険な変更や不明な点がある場合は、実装前にKazumaxへ確認してください。
また、Airが直接コードを修正する場合は、どれほど軽微な修正であっても、他エージェントとのGit衝突を防ぐため必ず事前にKazumaxの許可を取ってください。

## 完了時の確認

作業完了時は、何を変更したか、どう確認したか、次に誰の何を待つかを明記してください。

## バージョン表記更新ルール

ユーザーに見えるツール本体や共有プロジェクトを更新した場合は、毎回バージョン表記を確認してください。
目的は、Kazumax、友達、Air、Dex、CC、アグなどが「いま見ているものが最新版か」を判断できるようにすることです。

必ず行うこと:

- コードやUIの実装変更を行った場合は、該当プロジェクトのバージョン表記を更新する。
- バージョン表記の場所が決まっていないプロジェクトでは、最初に `README.md`、画面フッター、設定ファイル、`docs/handoff/CURRENT_STATUS.md` のどこで管理するかを決める。
- Handoffや完了報告には、変更後のバージョン番号または識別できるcommit hashを書く。
- 文書だけの軽微な更新でバージョンを上げない場合は、「バージョン変更なし。理由: 文書のみ」など理由を残す。

禁止:

- 実装を変えたのに、画面やREADMEのバージョン表記を古いまま放置すること。
- 複数プロジェクトで同じバージョン番号を混ぜて扱うこと。
- 「たぶん最新版」と曖昧に報告すること。

## Git共同作業の交通整理

GitHubなどの共有リポジトリで複数人・複数AIが作業する場合は、更新が混ざらないように以下を守ってください。

基本:

- 作業前に `git pull --ff-only` で最新版を取得する。
- 作業後は、変更内容、確認結果、次担当を `docs/handoff/` に残してからcommit/pushする。
- conflictが出た場合は勝手に解決せず、停止してKazumaxへ報告する。
- `.env`、パスワード、APIキー、本物DB、個人情報はcommit/pushしない。

同時作業する場合:

- 同じファイル・同じ機能を同時に触らない。
- 片方がmainへpushする前に、もう片方は作業を止めるか、別branchで作業する。
- 重要な実装や大きな変更では、`main` へ直接pushせず、作業branchを作ってからmergeする運用を優先する。
- 「誰がmainへ反映するか」を1人または1AIに決める。複数人が同時にmainへ押し込まない。

簡単運用:

- 慣れるまでは「mainを触るのは一度に1人だけ」にする。
- 友達側が作業中なら、Kazumax側はレビューや別プロジェクト作業に回る。
- Kazumax側がmainへ反映する前に、友達側の作業をpushしてもらい、こちらでpullしてから統合する。

branch運用:

- 共同作業が増える場合は、main直作業ではなく作業用branchを使う。
- mainは安定版の置き場、branchは作業机として扱う。
- 作業サイクル開始時は、mainを最新化してからbranchを作る。
- merge前にもmainへ移動し、`git pull --ff-only` で最新版を取得する。
- mergeは時間だけで決めず、「1サイクル完了」「レビューOK」「人に見せられる小さい完成単位」で行う。
- 文書やhandoffの追加は早めにmergeしてよい。DB、保存形式、自動生成ロジック、大きなUI変更はレビュー後にmergeする。

P4 OK後の統合担当:

- 作業branchからmainへのmergeが必要な共同プロジェクトでは、CCが実装・検証・commit・作業branchへのpushを担当し、DexがP4レビュー後のP5（統合・完了処理）を担当する。
- Dex(P5)は、P4でレビューしたcommitとmerge対象が同一であることを確認し、mainで`git pull --ff-only`を実行してからmerge・pushする。
- Dex(P5)は実装コードを追加修正しない。修正が必要ならCCへ差し戻し、再度P4レビューを行う。
- mainの更新、conflict、レビュー済みcommitの変化、未解決の必須確認がある場合はmergeせず停止し、Kazumaxへ報告する。
- Dex(P5)はmerge後、`CURRENT_STATUS.md`、handoff、commit hash、push結果、最終`git status`を確認して完了する。
- merge工程が存在しないローカル単独プロジェクトやmain直運用ではP5を追加せず、従来どおりP4 OK後にKazumaxへ返す。

衝突を減らすルール:

- 作業前に、今回触る予定ファイルと衝突しそうな場所を確認する。
- 同じファイル・同じ機能を同時に触りそうな場合は、作業前に担当を分ける。
- `App.jsx`、`main.py`、`models.py`、`CURRENT_STATUS.md`、`README.md`、依存関係ファイルなど中心ファイルは衝突しやすいので注意する。
- `CURRENT_STATUS.md` は、可能ならmainへmergeする担当だけが最後に更新する。

conflict発生時:

- AIは勝手に都合よく解決しない。
- 衝突ファイル、main側の内容、branch側の内容、統合案を短く報告する。
- 重要な衝突では、Kazumaxまたは担当者の判断を待つ。
- 解決後は、衝突マーカー（`<<<<<<<`, `=======`, `>>>>>>>`）が残っていないことを確認してからcommit/pushする。

## Kazumax確認負担の最小化

AIチームは、Kazumaxに毎回なんとなく「確認してください」と投げないでください。途中確認は原則としてAI側で完結させ、Kazumaxには本当に人間の判断が必要な箇所だけを渡します。

Dex(P4)がOK判定を出す場合、P4ファイルとチャット報告に **Kazumax確認レベル** を必ず明記してください。

- `確認不要`: 文書整理、内部修正、AI側のcompile・静的確認・実機確認で十分なもの。Kazumaxがすぐ触る必要はない。
- `軽い確認`: UIや通常導線に影響するが、AI側で主要検証済みのもの。Kazumaxには1〜5個程度の短いチェックだけ渡す。
- `必須確認`: 金額、Excel、公式提出書類、本番公開、VPS移行、データ削除・移行、または人間の業務感覚が必要なもの。Kazumax向けに具体的な確認手順を短く出す。

禁止:

- 「一通り見てください」「適当に触ってください」のような曖昧な依頼。
- AI側で確認できるcompile、diff、git status、静的検索、既存テストをKazumaxに丸投げすること。
- 長いチェックリストをチャットに出して、結局Kazumaxの負担を増やすこと。

推奨:

- P4 OK時は「今回は確認不要」「今回は軽い確認だけ」「今回は必須確認」のどれかを明言する。
- 確認が必要な場合は、Kazumaxが見るべき箇所を具体的に絞る。
- 金額・Excel・公式帳票は、AI側で検証済みでも、最終提出前だけKazumax確認を残す。
- 途中サイクルでは、Kazumax確認を省略できるなら省略する。

## CURRENT_STATUS軽量化ルール

`docs/handoff/CURRENT_STATUS.md` は、毎回最初に読む「現在地の入口」です。ここが長すぎると、AIが古い情報に引っ張られたり、毎回の読み込みトークンが増えたりします。

必ず以下を守ってください。

- `CURRENT_STATUS.md` の先頭には、最新サイクル、現在地、次担当、今回読むべきファイル、Stop Conditionsだけを書く。
- 完了済みサイクルの長い履歴、古いチェックリスト、古い次担当文、長い読むべきファイル一覧は残さない。
- 過去情報が必要な場合は、`docs/handoff/STATUS_ARCHIVE.md` または各サイクルのhandoffファイルへ移す。
- フェーズを動かしたAIは、`CURRENT_STATUS.md` を更新するときに「古い情報が入口に残っていないか」も確認する。
- 目安として、`CURRENT_STATUS.md` は100行以内を維持する。超える場合は、古い部分をアーカイブする。
- 重要ルールは日本語だけでなく、`DO NOT DELETE /export`, `app.version`, `Cycle 17` のようなASCIIの目印も併記するとよい。

## 次担当トリガー文の必須出力

差し戻し、実装依頼、再レビュー依頼、次担当への正式な作業開始など、Kazumaxが別AIのチャットへそのまま貼る必要がある場面では、担当AIは必ずチャットの最後にコピー用の起動メッセージを単独のテキストブロックで出力してください。

このルールの目的は、Kazumaxが毎回文章を作り直す手間をなくし、Air / Dex / CC の引き継ぎを迷わせないことです。

必須条件:

- テキストブロック内だけをコピーすれば、次担当AIがすぐ動ける内容にする。
- 最初に読むファイル、読了報告ゲート、今回読むべきhandoffファイル、作業内容、保存先、完了時の報告先を入れる。
- 差し戻しの場合は、NG理由の詳細ファイルとTake番号を明記する。
- チャット本文の説明に埋め込まず、必ず独立したコードブロックとして出す。
- すぐ次担当へ渡す必要がない完了報告や、Kazumaxへの説明だけで終わる場合は不要。

普段用の例:

```text
まず AGENTS.md、docs/handoff/CURRENT_STATUS.md、manuals/STARTUP_CHECKLIST.md を読んで、現在地・次担当・今回読むべきファイルを確認して。
このプロジェクトに docs/PROJECT_RULES.md や docs/handoff/WORKFLOW_RULES.md がある場合は、それも読んで危険領域と完了時ルールを確認して。
今回指定されたhandoffファイルを読み、作業前に「読了報告」と「詳細マニュアル追加読みの有無・理由」を短く出してから作業して。
長文レビューや次担当への正式引き継ぎは docs/handoff/ に保存し、チャットは短い合図文だけにして。
プラスアルファ提案がある場合は docs/proposals/ にも同じ内容を保存して。

CCへ：
DexがCycle XXのP4レビューを行い、Take2差し戻しになりました。
docs/handoff/P4_Rollback/xxxx.md を読んで、指摘内容を修正し、完了報告を docs/handoff/P3_CC_to_Dex/xxxx_take2.md に保存してください。
```

危険タスクでは、普段用に以下の1行を追加する:

```text
今回は金額・DB・Excel・保存処理などの危険領域に触る可能性があるため、manuals/AI_TEAM_WORKFLOW.md と manuals/WORKFLOW_RULES.md も追加で読んでから進めて。
```

## サブエージェント（並行処理）の積極活用プロトコル

真の最高効率を叩き出すため、各AIは以下のルールに従ってサブエージェント（内部プロセス）を活用してください。ただし、サブエージェントは調査・読解・確認・レビュー補助のために使うものであり、Air / CC / Dex の役割、実装判断、最終判断、担当AIの責任を代替してはいけません。

1. **並行処理による時短（積極活用）**
   巨大ファイルの解析、最新技術のWebリサーチ、複数ファイルの同時確認、複数観点レビューなど、裏で並行処理させた方が早く安全に終わると判断したタスクについては、AIは自身の権限で利用可能なサブタスク機能・並行レビュー機能を積極的に活用すること。速度だけでなく、リスク、観点数、検証負荷、責任分界も考慮して判断する。
2. **無駄な乱用の禁止（最高効率の追求）**
   サブエージェントの起動にはタイムラグ（オーバーヘッド）が発生するため、メインAI単体で瞬時に処理できる軽微なタスクには使用しないこと。常に「どちらが最速で最高効率か」を計算して判断する。
3. **明確な稼働報告の義務化**
   サブエージェントを利用した際は、通常のトラッキングタグや合図文の邪魔にならない短さで、チャット画面に `[⚡〇〇クルー稼働中: 〇〇の理由で〇〇を並行処理させています]` というタグを出力し、Kazumaxへ「使用した理由と目的」をひと目でわかるように報告すること。

## チーム内でのサブエージェントの呼称規則（〇〇クルー）

Air、Dex、CCといった「実体のあるメインエージェント」と、彼らが呼び出す「裏方の補助役（サブエージェント）」を混同しないよう、Kazumax向けの呼称ではサブエージェントを必ず **「〇〇クルー」** と呼ぶこと。内部メモで `SubReview-A` などのラベルを使ってもよいが、チャット報告やP2/P4本文では「デクスクルーA」のように誰の補助役か分かる名前へそろえる。
- 例：Airが立ち上げたサブエージェント ⇒ **エアクルー** (Air Crew)
- 例：Dexが立ち上げたサブエージェント ⇒ **デクスクルー** (Dex Crew)
- 例：CCが立ち上げたサブエージェント ⇒ **CCクルー** (CC Crew)

## サブレビュー利用時の記録

DexがP2事前監査またはP4レビューでサブエージェントを使った場合、サブエージェントの出力をそのまま最終判断にしないでください。Dexが内容を読み、採用・不採用・保留を判断し、最終的なOK/NGまたはCC向け修正指示として統合します。

P2/P4ファイルには、以下を短く残してください。使わなかった場合でも、高リスクなのに省略したときは理由を残してください。

- なぜサブレビューを使ったか。
- どの観点を任せたか。
- Dexが最終的にどう判断したか。
- 主な指摘ごとの採用 / 不採用 / 保留と理由。
- 残っているリスク。

サブエージェントの意見が割れた場合も、最終判断者はDexです。責任の所在をぼかさないでください。
Kazumaxへのチャット報告には、以下のように短く書いてください。

```text
サブレビュー利用判断: 使用。理由: 金額・Excel・条件保持に触るため、複数視点で確認しました。
```

```text
サブレビュー利用判断: 不使用。理由: 文言修正のみで影響範囲が狭いため、Dex単独で確認しました。
```

## DexによるCCクルー利用指示

Dex(P2)が危険タスクの事前監査を行う場合、CC(P3)向け指示書に **CCクルー利用判断: 不要 / 推奨 / 必須** を明記できます。

- `不要`: 変更範囲が狭く、CC単独の実装・検証で十分な場合。
- `推奨`: 実装範囲が広い、検証観点が多い、またはCCが不安を感じそうな場合。
- `必須`: 金額、DB、Excel、削除、一括処理、データ移行、本番前/VPS前確認などが複数重なる場合。

DexがCCクルー利用を `推奨` または `必須` と判断した場合、P2指示書には以下を含めてください。

- CCクルーを使う理由。
- CCクルーに確認させる観点。
- CCのP3報告書にCCクルー結果をどう保存・要約するか。
- CCクルーはDex(P4)の代替ではなく、CC側のセルフレビューであること。

CC(P3)は、DexからCCクルー利用指示がある場合、P3報告に「CCクルー補助レビュー結果」または「不使用理由」を必ず記録してください。
## 共通マニュアル更新ルール

共通ルールを変更したAIは、変更作業の最後に必ず同期まで行います。

手順:

1. `C:\Users\kazum\OneDrive\デスクトップ\AI共通マニュアルテンプレ` を更新する。
2. `C:\Users\kazum\OneDrive\デスクトップ\マニュアル同期.ps1` を実行する。
3. 同期先で `AGENTS.md` と `manuals/WORKFLOW_RULES.md` が更新されていることを確認する。
4. 進捗ファイルやプロジェクト固有ルールは上書きしない。

同期するもの:

- `AGENTS.md`
- `CLAUDE.md`
- `.cursorrules`
- `manuals/`

同期しないもの:

- `docs/handoff/CURRENT_STATUS.md`
- `docs/handoff/` のサイクル記録
- `docs/handoff/WORKFLOW_RULES.md`
- `docs/proposals/`
- `docs/PROJECT_RULES.md`

## P1・P2差し戻しの実装補助

DexがP4でP1またはP2の差し戻しを出すときは、通常のNG理由に加え、次の4点を短く添える。目的は、次担当が仕様の再解釈に時間を使わず、修正と検証へ集中できるようにすること。

1. **修正対象**: 主なファイル・関数・状態またはデータのどこを直すか。
2. **期待する状態遷移**: 成功・失敗・明示操作時に、何を変更し、何を保持するか。
3. **受入確認**: 再現可能な3〜5件程度の確認ケース。必要なら保存データ、既存値、エラー経路も含める。
4. **触らない範囲**: 今回変更しない仕様・既存挙動・別Takeへ送る事項。

P3実装担当は、この補助を実装の代わりとせず、P4差し戻し本文とプロジェクト固有ルールを正として対応する。P3報告には、各受入確認をどう検証したかを記録する。

P3相当以下の軽微な文言・見た目のみの修正には、原則としてこの4点の追加は不要。状態保持、保存、計算、外部連携、複数条件が絡むP1・P2に限定して簡潔に使う。
