# AI Team Workflow

このドキュメントは、Kazumax、Air、Dex、CCで作業するための共通フローです。

## 基本方針

P2は「必ずDex」ではありません。
タスクの危険度によって、AirがCCへ直接渡す場合と、Dexが事前監査する場合に分かれます。

## P0 技術選定・作り方確認

新しいプロジェクトを始めるときは、実装に入る前に必ず P0 として「作り方の確認」を行います。
Kazumaxは「何を作りたいか」「誰が使うか」「何が面倒か」「失敗すると困るものは何か」を伝えれば十分です。サーバー、DB、言語、フレームワーク、既存サービス利用の要否はAIチーム側が提案します。

Air(P1)は、最初の設計時に以下を確認してください。

- 見せるだけのサイトか、保存・計算・出力を行う業務ツールか。
- DB、ログイン、Excel/PDF出力、外部サービス連携、複数人利用が必要か。
- 自分のPCだけで使うのか、スマホや本番公開まで考えるのか。
- サーバーなし、サーバーあり、既存サービス利用のどれが一番ラクで安全か。
- 将来の修正や機能追加がしやすい構成か。
- Kazumaxが知らないことで損しそうな便利な選択肢がないか。

P0の結果は、`docs/handoff/P1_Air_Blueprint/` または `docs/proposals/` に短く保存します。
金額、DB、Excel、公式書類、保存処理などが絡む場合は、Airだけで決めずDexへ事前監査を回してください。

## 途中開始プロジェクトの棚卸

すでに「とりあえず作り始めた」プロジェクトで苦戦している場合は、いきなり作り直さず、まず途中棚卸を行います。
目的は、今ある努力をできるだけ活かしながら、設計・技術選定・仕様のズレを早めに見つけることです。

棚卸では以下を確認してください。

- 最初に作りたかったものと、今できているものの差。
- どこで詰まっているか。仕様、UI、データ構造、計算ロジック、技術選定、検証不足のどれか。
- サーバー、DB、フロントだけ、既存サービス利用など、今の構成が目的に合っているか。
- 捨てるべき部分、残すべき部分、作り直すより直した方がよい部分。
- 次に進むための最小サイクル。大きく全部直さず、1サイクルで確認できる大きさに分ける。

特にシフト作成、予約管理、在庫管理、会計、補助金帳票のように「条件が多く、保存や自動計算が必要なツール」は、途中棚卸の価値が高いです。
Airは棚卸案を作り、危険度が高い場合や技術選定の見直しが必要な場合はDexへ回してください。

## 通常タスクの流れ

軽いUI調整、文言修正、レイアウト調整、モック段階の小さな追加などは、AirがP1とP2相当の実装指示をまとめて作り、CCへ直接渡してよいです。

```text
Kazumax -> Air(P1/P2統合) -> CC(P3) -> Dex(P4レビュー) -> Kazumax
```

1. P1/P2 Air: Kazumaxと壁打ちし、仕様とCC向け実装指示をまとめる。
2. P3 CC: Airの統合指示書に従って実装し、検証結果を報告する。
3. P4 Dex: CCの差分をレビューし、OKまたは差し戻しを判断する。
4. Kazumax: 最終確認し、次サイクルへ進むか決める。

## 危険タスクの流れ

DB、保存処理、金額計算、Excel出力、外部通信、既存データ破壊の可能性がある変更、またはKazumax/Airが不安を感じる変更は、Dexの事前監査を挟みます。

```text
Kazumax -> Air(P1/P2草案) -> Dex(P2事前監査) -> CC(P3) -> Dex(P4レビュー) -> Kazumax
```

1. P1/P2草案 Air: 仕様とCC向け実装案を作る。
2. P2 Dex: Airの草案を読み、リスクを潰した安全なCC向け指示書にする。
3. P3 CC: Dexの指示書に従って実装し、検証結果を報告する。
4. P4 Dex: CCの差分をレビューし、OKまたは差し戻しを判断する。
5. Kazumax: 最終確認し、次サイクルへ進むか決める。

## P2をDexへ回す条件

以下のどれかに当てはまる場合、AirはCCへ直行せずDexへ回してください。

- 保存処理、DB、API、外部通信に触る。
- 金額、集計、帳票、Excel、日付計算に触る。
- 既存データを壊す可能性がある。
- 変更範囲が複数ファイル・複数責務にまたがる。
- 指示内容に曖昧さが残っている。
- Kazumaxが「Dexにも見てもらって」と言った。
- Air自身が少しでも危険だと判断した。

## P5 統合・完了処理（共同branch運用時のみ）

GitHub等で作業branchからmainへのmergeが必要な共同プロジェクトでは、Dex(P4)がOK判定を出した後、DexがP5として統合・完了処理を担当します。
ローカル単独運用やmain直運用など、merge工程が存在しないプロジェクトではP5を設けず、従来どおりP4 OKでKazumaxへ返します。

共同branch運用時の責任分担:

1. CC(P3): 実装、検証、commit、作業branchへのpushを行う。
2. Dex(P4): push済みcommitのDIFFをレビューし、OKまたは差し戻しを判断する。
3. Dex(P5): P4でレビューしたcommitとmerge対象が同一であることを確認し、mainを`git pull --ff-only`で最新化してからmerge・pushする。
4. Dex(P5): `CURRENT_STATUS.md`、handoff、commit hash、push結果、最終`git status`を更新・確認して完了する。

Dex(P5)は実装コードを追加修正してはいけません。修正が必要になった場合はP4 OKを取り消し、CCへ差し戻して再レビューします。

以下の場合、Dexはmergeせず停止してKazumaxへ報告します。

- mainがP4レビュー後に更新され、レビュー済み差分との関係を安全に確認できない。
- conflictが発生した。
- mergeによってレビュー済みcommitの内容が変わる。
- Kazumax確認レベルが`必須確認`で、merge前確認が指定されている。
- 本番公開、DB移行、データ削除など、mergeを超える外部影響がある。

## サブエージェント活用ルール

サブエージェントは、Air / CC / Dex の役割を置き換えるものではありません。必要な場面だけ、担当AIの判断を補強するために使う「専門チェック係」として扱います。

原則として、サブエージェントを使うかどうかは、その作業を担当しているAIが判断します。特にDexは、P2事前監査またはP4レビューに入る時点で、差分の危険度を見てサブレビューを入れるか判断してください。Kazumaxから明示指示がなくても、危険度が高い場合はDex判断でサブレビューを使ってよいです。`サブレビュー利用判断: 使用/不使用。理由: ...` を、作業開始時または完了報告時にKazumaxへ短く伝えてください。

### Dexレビューでの推奨形

Dexが最終レビュアーであることは変えません。サブエージェントは個別観点の調査・確認だけを行い、最終的なOK/NG判定、差し戻し内容、CCへの修正指示はDexが統合して決めます。

```text
SubReview-A: 金額・集計・Excelセル・帳票出力だけを見る
SubReview-B: UI導線・hidden input・条件保持・画面遷移だけを見る
SubReview-C: 既存機能の回帰・差分範囲・未報告ファイル混入だけを見る
Dex: サブレビュー結果を読み、最終P2/P4判断を出す
```

### DexによるCCクルー利用指示

危険タスクでDex(P2)が事前監査を行う場合、DexはCC(P3)向け指示書の中で **CCクルー利用を「不要 / 推奨 / 必須」のいずれかで指定できます**。

このルールの目的は、軽い作業では余計なトークンを使わず、重い作業だけCC側のセルフレビューを厚くすることです。通常タスクはAirがCCへ直接渡すため、Dexが関与しないまま進んでかまいません。危険タスクだけDexに回り、そこでさらにリスクが高いと判断した場合にCCクルー利用を指示します。

判断基準:

- `不要`: 変更範囲が狭く、compileや静的確認で十分に安全確認できる。
- `推奨`: 実装範囲が広い、複数画面・複数Controllerにまたがる、検証観点が多い、またはCCが不安を感じそうな場合。CCは状況に応じて使い、使わなかった場合はP3報告に理由を書く。
- `必須`: 金額、DB、Excel、削除、一括処理、データ移行、本番前/VPS前確認などが複数重なる場合。CCは実装後にCCクルーでセルフレビューし、結果をP3報告に含める。

DexがCCクルー利用を指定する場合、P2指示書には以下を必ず書きます。

- なぜCCクルーが必要か。
- CCクルーに確認させる観点。
- CC本体のP3報告に、CCクルー結果をどのように保存・要約するか。
- CCクルーはDex(P4)の代替ではなく、CC側の事前セルフレビューであること。

指示例:

```text
## CCクルー利用指示

今回の実装は、変更範囲が広く、DB・金額・Excel・削除・既存データに影響する可能性があるため、CC(P3)は実装完了後にCCクルーを使ってセルフレビューしてください。

CCクルーに確認させる観点:
- P2指示書の必須条件をすべて満たしているか
- 変更対象外の機能を壊していないか
- 金額計算、DB保存、Excel出力、削除・上書きに危険な差分がないか
- compile / version / git status の報告に漏れがないか
- 未追跡ファイルや不要ファイルが混入していないか

CCクルー結果は、CCのP3報告書に「CCクルー補助レビュー結果」として要約し、必要なら詳細ファイルを docs/handoff/P3_CC_to_Dex/ に保存してください。

ただし、CCクルーのレビューはDex(P4)の代替ではありません。最終OK/NGはDexが判断します。
```

### サブエージェントを使う判断基準

以下のどれかに当てはまる場合、Dexはサブレビューの利用を検討してください。特に金額、DB、Excel、既存データ破壊、外部通信、認証・権限、削除・上書き、データ移行、秘密情報に触る場合は、原則としてサブレビューを使います。使わない場合は、P2/P4ファイルとKazumaxへの報告に理由を明記してください。

- 金額計算、集計、帳票、Excel出力、セル座標に触る。
- DB保存、DB読込、mapper、schema、既存データに触る。
- API、外部通信、認証・権限、課金や外部サービス連携に触る。
- 削除、上書き、データ移行、バックアップ、ロールバック、秘密情報や個人情報に触る。
- hidden input、検索条件、対象データの絞り込み、画面遷移により出力対象が変わる。
- 差分が大きい、または複数責務にまたがる。
- Take2 / Take3 以降で、同じ領域の見落としを防ぎたい。
- Dexひとりのレビューでは観点が多すぎると判断した。

以下の場合は、原則としてサブエージェントを使わなくてよいです。

- 文言修正だけ。
- マニュアルやhandoffの軽微な整理だけ。
- 小さいCSS/UI調整だけ。
- 影響範囲が狭く、Dexひとりで十分に確認できる。

### 汎用例

```text
例1: 金額Excel出力の修正
Dexはサブレビューを入れる。金額・Excel担当、UI条件保持担当、回帰確認担当に分ける。

例2: ボタン文言の変更
Dex単独レビューでよい。サブレビューは使わない。

例3: 検索条件を保持してダウンロードする導線の修正
Dexは必要に応じてサブレビューを入れる。特にhidden input、GET/POSTパラメータ、対象件数の変化を見る担当を置く。
```

### 記録ルール

サブレビューを使った場合、DexのP2/P4ファイルに以下を短く記録してください。サブレビューを使わなかった場合も、Kazumaxへの報告に不使用理由を短く添えてください。高リスクなのに使わなかった場合は、P2/P4ファイルにも省略理由を残してください。

- サブレビューを使った理由。
- サブレビューに割り当てた観点。
- サブレビュー結果をDexがどう統合したか。
- 主な指摘ごとの採用 / 不採用 / 保留と理由。
## Air自身による実装（直直し）の厳格な禁止ルール

Airは原則として企画・設計（Blueprint作成）を担当し、実装は専任のCC（P3）が行います。

以下のルールを**厳守**してください。
1. **Airの直接実装の原則禁止**: Airが勝手にソースコードを編集してはならない。実装担当はCC（P3）であり、役割境界を越えて独断でコードを書き換える行為はチーム運用を混乱させるため厳禁とする。
2. **事前口頭承認の絶対義務**: 例外的に「軽微なドキュメント修正」や「Kazumaxからの直接依頼」でAirがコードに触る場合でも、必ず事前チャットでKazumaxに「これはAirが直接修正してよろしいですか？」と確認し、明示的な口頭承認を得てからのみ行うこと。
3. **進行中指示書と壁打ち仕様の厳密分離**:
   - CCが作業中のサイクル指示書（P2）に書かれていない追加仕様を、チャットでの壁打ち段階で「もうCCが作っている」「実装中である」と偽って回答・誤認させてはならない。
   - CCが今作っている内容は、必ず **『対象のP2指示書ファイルに記載されている内容のみ』** を正としてユーザーへ回答すること。壁打ちで決定した新要件は、指示書を更新（Take改訂）して正式にCCへ引き継ぐまで「次回以降の実装予定」として管理すること。

## Handoff Protocol

長い指示や報告は、チャットだけでなくファイルに保存します。

推奨フォルダ例:

- `docs/handoff/P1_Air_Blueprint/`
- `docs/handoff/P2_Dex_to_CC/`
- `docs/handoff/P3_CC_to_Dex/`
- `docs/handoff/P4_Dex_Review/`
- `docs/handoff/P4_Rollback/`
- `docs/proposals/`

Airが通常タスクとしてCCへ直接渡す場合も、指示書は `docs/handoff/P1_Air_Blueprint/` などに保存してください。
DexがP2事前監査を行う場合は、CC向け最終指示書を `docs/handoff/P2_Dex_to_CC/` に保存してください。

## 次担当への起動メッセージ

差し戻し、実装依頼、再レビュー依頼など、Kazumaxが別AIを起動する必要がある場合は、作業したAIがそのまま貼れる起動メッセージを必ずチャットへ出します。

```text
まず AGENTS.md、docs/handoff/WORKFLOW_RULES.md、docs/handoff/CURRENT_STATUS.md を読んで、現在地・次担当・完了時ルールを確認してから作業して。
このプロジェクトに docs/PROJECT_RULES.md がある場合は、それも読んで危険領域と検証条件を確認して。

CCへ：
DexがCycle XXのP4レビューを行い、Take2差し戻しになりました。
docs/handoff/P4_Rollback/xxxx.md を読んで、指摘内容を修正し、完了報告を docs/handoff/P3_CC_to_Dex/xxxx_take2.md に保存してください。
```

起動メッセージは、Kazumaxが説明文を足さなくても次担当AIが迷わず動ける粒度にします。差し戻し先、読むファイル、作業内容、保存先を必ず入れてください。

## サイクル番号

サイクル番号はプロジェクトごとに管理します。

- 既存プロジェクト: `docs/handoff/CURRENT_STATUS.md` の Current cycle を読む。
- 新規プロジェクト: Cycle 1 から開始する。
- 別プロジェクトのサイクル番号を引き継がない。

## 進捗管理

現在の状況は必ず `docs/handoff/CURRENT_STATUS.md` にまとめます。
このファイルだけはプロジェクト固有です。共通テンプレからコピーした後、プロジェクト名とサイクル番号を更新してください。
