## 2. 生成UIの整理

### 2-1. 日常操作

- PCの全体シフト表では、`空欄自動作成`を一番分かりやすい主ボタンとして残す。
- 既存の挙動を変えない: 入力済みセルを固定し、空欄だけを自動作成する。
- `希望休ランダム入力`は日常操作として残す。
- `最適化シフトを生成`を、日常操作と同じ列・同じ強さのボタンとして常時表示しない。

### 2-2. 再最適化は上級操作へ

- `generateShift()`を削除・改名・別ロジック化しない。呼び出し導線だけを上級操作へ移す。
- PCでは、既存デザインに合う`詳細操作`ボタンから到達できるようにする。トグルには`aria-expanded`と、対応する領域への`aria-controls`を付ける。
- 上級操作内の実行ボタン名は、通常の空欄作成と区別できる`最適化シフトを再生成`等にする。
- 実行前に必ず確認を出す。文面は次を意味的に満たすこと: 「手動入力済みセルは保持し、自動生成された部分を再配置・作り直す」。キャンセル時は`fetch`、履歴、表、isGeneratingを一切変更しない。
- スマホではハンバーガーメニュー内で、`日常操作`（空欄自動作成、希望休ランダム）と`上級・再調整`（最適化再生成）を視覚的に分ける。上級操作の確認後はメニューを閉じる。
- tab切替、生成開始、全画面切替などで開いた詳細操作が背面に残って誤操作できない状態にする。

### 2-3. 既存テストの移行

`最適化シフトを生成`という常時表示のDOMを前提にしているテストは、検索で漏れなく更新する。

- 機能テストは、上級操作を開く -> 確認を承認 -> `generateShift()`が呼ばれる、というユーザー操作を通す。
- 確認ダイアログをテストで承認/拒否できるよう`window.confirm`をmockし、拒否ケースも追加する。
- 表示の存在だけを確認するテストは、主操作に`空欄自動作成`、上級操作に再最適化があることを確認する。
- テストを通す目的で、ユーザーから見えない常時表示ボタンやテスト専用の実装分岐を追加しない。

## 3. スタンプのトグル空欄化

既存の`isStampNoOp()`による「同じスタンプなら何もしない」仕様は廃止する。

- 通常のスタンプが既存セルの`shift`と同じ場合、そのセルを完全な空欄オブジェクト`{}`へ置き換える。
- `hours`、`note`、`isFixed`、`isError`、その他のセル固有属性を残してはいけない。
- 同じスタンプ消去は、通常シフトの許可判定より**先**に判定する。許可シフト設定が後から変わっていても、同値セルを消去できること。
- 同値でない通常スタンプは、従来どおり許可判定を行い、許可されていれば上書き、許可されていなければ変更しない。
- 消去・上書きのどちらも`commitHistory()`を一度だけ通し、`setGeneratedResult()`と`buildRequestsFromMatrix()`を同じ履歴操作内で実行する。
- 希望休を消したときは`employees[].requests`から該当日を即時に消す。Undoで元の希望休・requestsを復元し、Redoで再び消す。
- 消去後もスタンプモードと選択中の筆を維持する。

## 4. 消しゴムと特殊シフトのスタンプ（Kazumax追加確定仕様）

トグル消去とは別に、スタンプパレットへ`消しゴム`を追加する。これは「表全体を一括削除」ではなく、**選択後にタップした各セルを連続で空欄にする筆**である。誤解を避け、表示名は`消しゴム`または`消しゴム（空欄にする）`とする。

- 特殊IDは通常・自由時間IDと衝突しない定数（例: `__erase__`）を使う。文字列を複数箇所へ直書きしない。
- `buildStampCandidates()`へ消しゴム候補を追加する。休・希望休・通常シフト・自由時間の既存候補を壊さない。
- activeStampが消しゴムの場合、許可シフト判定を通さず、入力済みセルを`{}`へ完全初期化する。
- 消しゴムで空欄セルを選んだ場合は真のno-opとする。履歴、Redo、matrix、requestsを変更しない。
- 消しゴムで通常シフト、希望休、自由時間、手動確定セル、過去の自動生成セルのいずれも消去できる。
- 消しゴムも短タップ、マウスクリック、キーボードEnter/Spaceで同じ結果にする。スワイプ、drag、スワップ、通常編集を起動しない。
- 消しゴムをスタンプ候補として選んだままルール設定を変えても、特殊IDとしてスタンプモードが勝手に終了しないようactiveStamp監視条件を更新する。
- パレット上で消しゴムと分かる表示・title・`aria-pressed`を用意する。必要なら危険色は控えめに使い、通常候補と同じ44px以上のタッチ領域を守る。

### 4-1. 特殊シフトを最初からスタンプ候補に入れる

有休、応援、勉強会、店長会は、通常シフトの許可リストやルール設定で毎回作るものではない。次の4種類を、常にスタンプパレットへ最初から表示する。

- `有休`
- `応援`
- `勉強会`
- `店長会`

`研修`、`公休`など、今回指定されていない既存の特殊シフトを勝手にスタンプ候補へ追加しない。従来どおりセル編集からの入力は維持する。

特殊シフトの現在の保存形式は、開始・終了時刻ではなく`hours`（計上時間）である。この形式を拡張しない。特殊スタンプを押した時だけ、早番`①`の時間帯を初期計上時間として使う。

- 現在の初期早番は`① 8:15〜12:15`であるため、初期値は`4h`となる。
- 実装は固定の`4`を散在させず、現在の`shiftMaster['①']`から時間差を安全に算出する小さな純粋関数にする。値が欠損・不正なら既存の`DEFAULT_SPECIAL_HOURS`へ安全にフォールバックする。
- 特殊スタンプで作るセルは、たとえば`{ shift: '有休', hours: 4, isFixed: true, isError: false }`のように`hours`を明示保存する。
- スタンプをOFFにして対象セルを通常どおり開けば、既存の特殊勤務用の時間入力から個別に`hours`を変更できること。スタンプ中に編集モーダルを開く仕様へ変えてはいけない。
- 4種類の特殊スタンプは、従業員ごとの通常シフト許可リストに含まれなくても使える。消しゴムと同様、通常シフト用の許可判定で拒否してはいけない。
- 同値特殊スタンプの再タップは、通常スタンプと同じく空欄化する。消しゴムも特殊セルを完全に空欄化できる。
- activeStamp監視では、消しゴムとこの4種類を特殊候補として扱い、`shiftMaster`の変更だけでスタンプモードを終了させない。

## 5. 純粋関数とテストの具体的改修

### 5-1. 旧テストの置換

- `cycle12Utils.test.jsx`の`isStampNoOp / buildStampedCell` describeを削除または新しい操作判定関数の仕様に置換する。
- `App.cycle12.test.jsx`の「同じシフトを同じセルへ重ねてもno-op」テストを、同値再タップで完全空欄化しUndo可能であるテストに置換する。
- 旧NoOpを残すのは、**消しゴムで空欄を選んだ場合だけ**とする。

### 5-2. 恒久回帰テスト

最低限、以下を追加・更新する。

1. 同値通常スタンプで、属性付きセルが`{}`へ完全初期化される。
2. 同値`希望休`スタンプで、matrixが空欄になり`employees[].requests`から対象日が消える。
3. 同値消去は1履歴だけ追加し、Undoで属性付き元セルとrequestsが完全復元、Redoで空欄へ戻る。
4. 許可リストから外れた通常シフトでも、同値セルの消去はalertなしで成功する。異なる通常スタンプは従来どおり拒否される。
5. 消しゴム候補と、有休・応援・勉強会・店長会の4候補がパレットに表示され、選択状態と現在の筆表示が正しく切り替わる。
6. 各特殊スタンプは、早番`①`から導いた初期`hours`を明示保存し、許可シフト一覧に含まれない従業員にも使える。早番時間が不正な場合は既存既定時間へフォールバックする。
7. 特殊スタンプで作ったセルを通常編集すると、初期`hours`から任意の有効な時間へ変更でき、同値再タップ・消しゴムでは`hours`やnoteを残さず空欄化する。
8. 消しゴムで通常シフト、希望休、自由時間、4種類の特殊シフトを消去でき、各ケースでrequests同期・属性全消去を確認する。
9. 消しゴムで空欄セルを選んでも履歴・Redo・matrix・requestsを変えない。
10. 消しゴムのキーボードEnter/Spaceとpointer短タップで同じ消去が起き、スワイプでは起きない。
11. スタンプON中は消しゴム・特殊スタンプでもセル編集モーダル・セル交換dragが起動しない。
12. PCでは空欄自動作成が主操作、詳細操作を開くと再最適化が現れ、確認キャンセルではfetchしない。スマホでも日常/上級セクション分離を確認する。
13. 全画面表示中もスタンプ開始、消しゴム・特殊スタンプ選択、消去、終了が操作でき、背面UIは引き続き`inert`である。

## 6. CCクルー利用指示

**CCクルー利用判断: 推奨。**

理由: UI導線、特殊スタンプ、履歴、希望休同期、既存の多数のDOMテストを同時に変更するため。

CCクルーに確認させる観点:

- 同値トグルと消しゴムの判定順・空欄no-opが仕様どおりか。
- 消去後にセル属性や希望休requestが残らないか。
- Undo/Redoと手動セル保護が壊れていないか。
- PC、スマホ、全画面、キーボード、pointer操作の到達性に漏れがないか。
- 特殊スタンプ4種類が通常シフト許可判定に誤って阻まれず、早番相当の初期`hours`と手動再編集を正しく扱うか。
- version、git diff、未追跡ファイル、テスト更新漏れがないか。

P3報告にはCCクルーの使用有無・結果・採用した指摘を短く記録する。CCクルーはDex(P4)の代替ではない。
