# Cycle 9 Dex(P2) 最終実装指示書

## 1. P2判定

AirのBlueprintは、セル直接編集・シフト交換・Undo/Redoを一体化する方針として採用します。

ただし、現行コードには次の重大な衝突があります。CC(P3)はBlueprintだけで実装せず、本指示書を優先してください。

1. 行全体のHTML Drag and Dropとセル交換が同時発火し得る。
2. セル全面を覆う透明な`select`が、タップ・スワイプ・ドラッグを横取りする。
3. 「希望休」は`matrix`と`employees[].requests`の二重管理で、matrixだけのUndoでは不整合になる。
4. 自由時間セルを既存形式と無関係なIDにすると、空欄自動作成時に固定セルとして認識されない。
5. Blueprintの画面幅境界は現行仕様と異なる。Cycle 9では「768px以下がスマホ、769px以上がPC」を正とする。

以上を解消する条件で実装可とします。

## 2. 作業範囲

作業ブランチ:

- `cc-cycle9`
- `main`へ直接mergeしない。
- 作業開始時に`git fetch origin`を行い、`cc-cycle9`が現在の`main`を基点としていることを確認する。
- 他者の未追跡ファイルや無関係な変更をcommitへ混ぜない。

主な対象:

- `frontend/src/App.jsx`
- `frontend/src/index.css`
- Cycle 9用の小さな純粋関数モジュール
- Cycle 9用テスト
- `docs/handoff/CURRENT_STATUS.md`
- P3報告書

変更禁止:

- バックエンド、API、DB、solver
- 締め日、従業員初期データ、自動生成制約
- Cycle 7の固定列・ズーム・スクロール設計
- Cycle 8の目標時間・希望休ランダム入力の仕様

想定外にバックエンド変更が必要になった場合は、推測で進めず停止してDexへ戻してください。

## 3. セル編集UI

### 3.1 入口

- セル全面の透明な`select`を廃止する。
- 各セルには`button type="button"`を置き、短いタップ、クリック、Enter、Spaceで編集画面を開く。
- `aria-label`には従業員名、日付、現在のシフトを含める。
- 表示中のシフト名、固定マーク、エラー色、希望休色は維持する。
- PCとスマホで同じ編集データを使い、画面幅だけで保存ロジックを分岐させない。

編集画面には最低限、次を配置する。

- 既存シフト選択
- 自由時間の開始・終了
- 注記
- セルを空にする
- このシフトを交換
- 保存
- キャンセル

既存の特殊シフト時間編集も同じdraftへ統合する。シフトを選んだ時点ではstateを変更せず、「保存」で1回だけ確定する。キャンセル、不正入力、同値保存ではセルも履歴も変更しない。

### 3.2 自由時間

- 入力条件は`00:00 <= start < end <= 24:00`。
- 開始時刻に`24:00`は不可、終了時刻のみ`24:00`可。
- 日付またぎはCycle 9対象外。
- 空欄、同時刻、逆転、不正形式は保存拒否し、編集画面を閉じない。
- 既存の時刻入力部品・`timeUtils`を再利用し、時刻計算を文字列切り貼りで重複実装しない。

自由時間はバックエンドを変えず、既存`shiftMaster`方式へ統合する。

- 安定した衝突しないIDを純粋関数で生成する。例: `__custom__10_00_15_00`
- `shiftMaster[id] = "10:00～15:00"`を登録する。
- セルの`shift`にはそのIDを保存する。
- 同じ時間帯は同じIDを再利用する。
- 空欄自動作成では、当該IDと時間を`shift_types`へ含め、固定割当にも同じIDを送る。
- 空欄自動作成のレスポンス適用後、既存固定セルの`note`等のフロント専用属性を再合成して消失を防ぐ。
- 集計表示、登録販売者判定、朝鍵・夜鍵判定でも`shiftMaster[id]`の時刻を利用する。

### 3.3 セルデータ

セルを保存する際は、不要な古い属性を残さない。

- 空セル: `{}`
- 通常シフト・自由時間: `shift`, `isFixed: true`, `isError: false`, 任意の`note`
- 時間指定が必要な特殊シフト: 上記に加えて有効な`hours`
- 通常シフトへ戻した場合は古い`hours`を削除する。
- 注記は前後空白を除去し、最大40文字とする。
- 注記はReactの通常テキストとして描画し、HTMLとして挿入しない。
- セル交換では一部の属性だけでなく、セルオブジェクト全体を交換する。

## 4. スマホの誤操作防止

スマホ判定は`window.innerWidth <= 768`とする。

Pointer Eventsで短タップとスワイプを区別する。

- `pointerdown`で`pointerId`、開始座標、開始時刻を記録する。
- 移動距離が8px以上、`pointercancel`、複数指、別pointerへの切替でタップ候補を破棄する。
- 350ms以内かつ移動8px未満の`pointerup`だけを短タップとする。
- スクロール操作で`preventDefault()`を呼ばない。
- セルと横スクロール領域の`touch-action`は`auto`または`pan-x pan-y`を維持する。
- スワイプ中に編集画面や交換確定を発火させない。
- 768px以下ではHTML Drag and Dropを使用しない。

スマホ交換:

1. 編集画面の「このシフトを交換」で交換元を選ぶ。
2. 交換待ちを明示する小さなバーとキャンセル操作を表示する。
3. 次の有効な短タップを交換先とする。
4. 同じセルの再タップは交換せずキャンセルする。
5. 横スクロールだけでは交換元を解除しない。
6. 月変更、タブ変更、生成開始、従業員構成変更、リセット、Undo/Redoで交換待ちを解除する。

## 5. PCのドラッグ競合防止

- 行全体の`draggable`を廃止する。
- 従業員並べ替えは左固定列の専用ドラッグハンドルだけを`draggable`にする。
- 行移動とセル交換には別々の状態を使う。
- dragデータに`kind: "employee"`または`kind: "cell"`を必ず入れる。
- セル交換は`employeeIndex`と`dayIndex`を持つ。
- 有効な交換先セルの`dragover`だけで`preventDefault()`する。
- 同じセル、範囲外、古いmatrix座標、操作途中で生成結果が変わった場合はno-opとする。
- `dragend`とEscapeでdrag状態を必ず消す。
- セルdragで行順が変わらず、行dragでセル交換が起きないことを保証する。
- キーボード利用者向けに、編集画面から交換元を選び、別セルをEnter/Spaceで選ぶ2点方式も使えるようにする。

## 6. 希望休同期

セル編集、セル交換、Undo/Redo、希望休ランダム入力、空欄自動作成、再生成後は、表示中matrixの「希望休」から`employees[].requests`を再構築する共通純粋関数を通す。

- 増分のpush/removeを複数箇所へ書かない。
- 重複日付を作らない。
- 従業員とmatrix行の対応を崩さない。
- Undo後、画面と次回生成payloadが完全一致する。

## 7. Undo/Redo契約

### 7.1 スナップショット

履歴はメモリ内だけに保持し、localStorageへ保存しない。再読込時は履歴0件で開始する。

1件のスナップショット:

```js
{
  generatedResult: structuredClone(generatedResult),
  employees: structuredClone(employees),
  shiftMaster: structuredClone(shiftMaster),
  label: "K.D. 6/10 の勤務時間変更"
}
```

- 最大20件。21件目で最古を破棄する。
- DOM、イベント、モーダルdraft、swap/drag状態、履歴自身は含めない。
- 参照共有を残さない。
- 毎操作で巨大な`JSON.stringify()`比較をしない。各操作の変更対象を比較してno-opを判定する。

従業員全体を含めるのは、行順と希望休をmatrixと原子的に戻すためである。その代わり、従業員の追加・削除・編集時には履歴を必ずクリアし、古いプロフィールをUndoで復元しない。

### 7.2 共通commit

matrixを変える処理は、変更前スナップショットを記録してから、関連stateを1トランザクションとして更新する共通commit関数を通す。

履歴対象:

- セル編集・空欄化
- 特殊シフト時間の保存
- セル交換
- 希望休ランダム入力
- 従業員行の並べ替え
- 自動生成の成功
- 空欄自動作成の成功

1回のユーザー操作につき履歴は1件だけとする。通信開始時には記録せず、成功レスポンスを適用する直前に記録する。通信失敗、キャンセル、不正入力、同値保存は履歴もfutureも変更しない。

履歴クリア:

- 月変更
- デフォルト構成リセット
- 従業員の追加・削除・プロフィール編集
- シフトマスターの手動構成変更
- matrixと従業員行の対応が保証できなくなる構造変更

履歴維持:

- タブ、ズーム、画面幅の変更
- 通信失敗
- モーダルのキャンセル
- 不正入力

新しい有効な変更を行ったらRedo側を全削除する。

### 7.3 操作と競合

- ツールバーにUndo/Redoのアイコンボタンを置き、tooltipと`aria-label`を付ける。
- 履歴がない側はdisabledにする。
- `Ctrl/Cmd+Z`でUndo。
- `Ctrl/Cmd+Shift+Z`または`Ctrl+Y`でRedo。
- `input`, `textarea`, `select`, `contenteditable`内ではブラウザ標準Undoを横取りしない。
- 編集画面のdraft入力中はグローバルUndo/Redoを発火させない。
- 実際にUndo/Redoできる場合だけ`preventDefault()`する。
- `isGenerating`中はセル編集、交換、Undo/Redoをdisabledにし、非同期レスポンスとの競合を防ぐ。
- Undo/Redo適用後に希望休を再同期し、編集画面・swap・drag状態を閉じる。
- state復元後に既存localStorage effectが最新状態を保存することを確認する。

## 8. 実装構造と性能

- 履歴操作、セル正規化、自由時間ID、希望休同期、セル交換は小さな純粋関数へ分離する。
- `App.jsx`へイベント条件をすべて直書きしない。
- 履歴は最大20件、表は現行規模を前提とし、無制限配列を作らない。
- pointer moveごとにReact stateやlocalStorageを書き換えない。座標追跡は`useRef`を使う。
- dragoverごとにmatrix全体をcloneしない。
- localStorageの既存キーと読込互換性を維持する。
- v4.30の既存データを読み込めること。履歴用データ移行は不要。
- 実装完了時にバージョンを`v4.31`へ1回だけ更新する。

## 9. 必須自動テスト

既存テストを削らず、Cycle 9の純粋関数テストを中心に追加する。小さな2人×3日程度のfixtureを使い、24人×31日のDOMを大量生成しない。

最低限:

1. 8px未満の短タップで編集画面が1回だけ開く。
2. 30px横スワイプ、`pointercancel`、複数指では開かない。
3. 768pxはスマホ方式、769pxはPC方式。
4. 透明selectがなく、セルbuttonをキーボードで開ける。
5. セルdragで従業員順が変わらない。
6. 行ハンドルdragで従業員とmatrix行の対応が崩れない。
7. セル交換で`shift`, `hours`, `note`, `isFixed`, `isError`を含む全属性が交換される。
8. 希望休の編集・交換・Undo後にmatrixと`employees[].requests`が一致する。
9. 自由時間が集計、登録販売者、朝鍵、夜鍵判定へ反映される。
10. 自由時間の固定セルが空欄自動作成payloadで有効なシフトIDになる。
11. 空欄自動作成後も自由時間と注記が保持される。
12. 特殊シフト・自由時間のキャンセルと不正入力で変更も履歴も発生しない。
13. Undo→Redoで3 stateが完全復元される。
14. Undo後の新規編集でRedoが消える。
15. 21回の変更で履歴が20件に制限される。
16. 同値保存と同じセルへのswapで履歴が増えない。
17. 入力中の`Ctrl/Cmd+Z`を横取りしない。
18. 再読込後は現在表だけ復元し、履歴は空。
19. `isGenerating`中は編集・交換・Undo/Redoできない。
20. Cycle 7固定列・ズーム、Cycle 8希望休ランダム・目標時間表示が回帰しない。

検証コマンド:

```text
npm --prefix frontend test
npm --prefix frontend test
node frontend/test_time_utils.mjs
npm --prefix frontend run build
git diff --check
```

- 標準テストを連続2回通す。
- 現行の`pool: "forks"`, `maxWorkers: 2`, `testTimeout: 20000`を維持する。
- タイムアウト値を延長して通した扱いにしない。
- テスト件数、各コマンドの結果、所要時間をP3報告へ記載する。
- 重い場合は巨大DOMテストを増やさず、純粋関数テストへ分離する。

- 横スワイプで編集画面が開かない。

## 11. CCクルー利用

**CCクルー利用: 必須**

理由:

- 状態3系統、localStorage、非同期生成、二種類のdragを同時に扱う。
- 実装者自身が見落としやすいイベント競合と履歴不整合が中心である。
- P4前に狙いを分けた補助レビューを入れる価値が高い。

CCクルーへ依頼する観点:

1. タップ・スワイプ・セルdrag・行dragのイベント競合、768/769境界、キーボード操作。
2. Undo/Redoの原子性、希望休同期、自由時間`shiftMaster`、非同期成功・失敗・no-op。
3. テストの偽陽性、実行時間、既存Cycle 7/8回帰、無関係ファイル混入。

CC本体は採用・不採用と理由をP3報告へ要約する。CCクルーはDex(P4)の代替ではない。

## 12. デクスクルー監査の反映

サブレビュー利用: 使用。

採用:

- 透明select廃止、行dragハンドル限定、drag種別分離。
- Pointer Eventsの距離・時間・cancel判定。
- 768px以下スマホ、769px以上PCへの統一。
- 希望休をmatrixから再構築。
- 自由時間と空欄自動作成のID連携。
- 特殊シフトをdraft化し、保存を1履歴へ統合。
- 純粋関数中心の高速テスト。

調整して採用:

- 履歴はmatrixだけでなく`generatedResult`, `employees`, `shiftMaster`を原子的に保存する。
- 自動生成・空欄自動作成は成功時に1履歴として記録し、失敗時は履歴を変えない。
- 自由時間は独立した未知IDのまま保持せず、既存`shiftMaster`とpayloadへ統合する。
