# P1 Blueprint: Cycle 13「生成UI整理とスタンプ再タップ消去（トグル動作）」マスター設計書

## 背景と戦略（日常運用の安全性向上と直感的なペイント消去への深化）
現在（v4.47）、Cycle 12までの実装により「手動入力の完全不可侵保護」および「スタンプ一括連続塗り」が確立し、実稼働における劇的な業務効率改善を達成しています。
Cycle 13 では、カズマ総監督による確固たる方針に基づき、**① 普段使いの生成UI導線明確化（「空欄自動作成」の主役化と再最適化機能の上級メニュー隔離）** と、**② 消しゴム要らずで直感的に連続操作できる「同値スタンプのトグル空欄化機能」** を実装し、さらなる誤操作撲滅と軽快なシフト調整を両立させます。

---

## 1. コア設計方針と要件 (MUST)

### (1) 自動生成ボタンUI導線の整理（主操作と上級操作の明確分離）
現行の「空欄自動作成」と「最適化シフトを生成 (再最適化)」が同列に並んでいる構成は誤打の原因となりやすいため、以下のように責務と表示順位を整理する。

- **主役操作（プライマリボタン）**:
  - **「空欄自動作成」** を、入力済みの手動および確定セルを全維持しながら余ったマスの合間だけを賢く埋める日常のメイン操作として、PC・スマホ共に見やすい一番最初の主導線に配置する。
- **上級操作（「最適化シフトを生成」の再構成と安全隔離）**:
  - `generateShift()` などの機能自体は一切削除せず、過去の自動生成セルを再計算して並び替える「上級・詳細リセット機能」として「詳細操作／その他メニュー」内に移管する。
  - **PC版デザイン**:
    - ヘッダー主要部に「✨ 空欄自動作成」「🎲 希望休ランダム入力」を前面配置し、隣接してセカンダリ外観（アウトライン調や設定歯車アイコン等）の「⚙️ 詳細操作 ▼（あるいは上級メニュー）」トグルボタン・ドロップダウンを配置。
    - ドロップダウン展開後または専用操作モーダル内から「🔄 最適化シフトの全面再構築 (上級)」を選択可能とする。
  - **スマホ版デザイン (768px以下)**:
    - 既存の「ハンバーガーメニュー（≡）」内において、上部の「日常操作（基本構成）」セクションに「空欄自動作成」「希望休ランダム」を提示。
    - 区切り線（セパレーター）を挟んだ下の「上級・再調整アクション」セクションに「最適化シフトを再生成」を配置し、視覚的に隔離する。
- **安全コンファーム（確認ダイアログ）の徹底**:
  - 上級の「最適化シフトの再生成」を実行しようとした際には、即座に計算を開始させず、必ず **「⚠️ 手動入力済みのセルは保持したまま、自動生成された部分を再配置・作り直します。よろしいですか？」** という確認モーダル（またはブラウザ `confirm` 等の明確な確認ポップアップ）を呈示し、明示的な承認を得てから処理を開始させる。

### (2) スタンプ再タップ消去（トグル空欄化機能）
スタンプモード作動中、筆先で掴んでいるシフト種別（①〜④や希望休など）と全く同じ内容がすでに設定されているセルを再度タップ（クリック）した場合、消しゴム機能を選びなおす手間をなくし、 **そのセルを完全な「未記入・空欄状態」へ一撃でリセット（消去）** する仕様へ進化させます。

- **具体的な動作フロー**:
  - 空欄へ `④` をスタンプ ➡ `④` が入力される。
  - すでに `④` のセルへ `④` を再度スタンプ（再タップ） ➡ セルが **「空欄」** へ戻る。
  - 空欄へ `希望休` (休) をスタンプ ➡ `希望休` が配置される。
  - すでに `希望休` のセルを `希望休` スタンプで再度タップ ➡ セルが **「空欄」** へ即時リセット。
- **判定優先順位と状態管理（安全性保証）**:
  - **許可シフト判定の超克**: 「同値であるかのトグル判定」は、従業員の許可シフト制約検証よりも **先に実施** すること。仮に後から従業員の許可シフト制限が変更されていたとしても、「既に貼られているセルと同じものを重ね押しして空き状態へ消す」操作は一切妨害せず確実に許可する。
  - **完全初期化義務**: セルの空欄化にあたっては、単純に `shift` の文字列を空文字に帰すだけでなく、**`hours`（労働時間）、`note`（備考コメント）、`isFixed`（確定ロック状態）、`isError`（エラーフラグ）等、セルに紐づくすべての固有情報を残留させずゼロリセット・初期化** すること。
  - **希望休との同期保証**: 希望休セル（「休」）が空欄へ戻された際、および再入力された際には、現行のマスター共通関数である `buildRequestsFromMatrix()` を即座に発動させ、**`employees[].requests` 内の希望休日リストから即時に同期・削除** する構図を損なわないこと。
  - **Undo/Redo (20件スタック) の原子性維持**:
    - 1回の「スタンプ消去（空欄化）」は、堂々と独立した **1回のUndo/Redo歴史操作（スタック記録）** として登録されること。
    - よって、誤って重ね連打して空にしてしまっても、**1度 Undo を押すことで「消される前のセル完全状態 (時間・ノート・確定状態含む)」を1発で完璧に復元** し、再度 Redo することで再び綺麗な空欄へ戻せる安心性を守り抜く。

---

### (3) 操作互換性・レスポンシブ干渉防衛 (Non-Break Guarantees)
- **入力デバイス共通性**: マウスクリック、スマホ・タブレットのタッチパネル（短タップ）、ならびにキーボード navigation の Enter / Space キースタンプいずれの操作においても、全く同一のトグル空欄化結果を導き出すこと。
- **スワイプ・ドラッグ・スワップ非干渉**: スマホ横スワイプ移動（8px以上の判定および pointercancel）、専用ハンドルでの行の並べ替え、2点タッチによるシフトスワップ交換、およびスタンプモードOFF時のセルクリック通常編集ポップアップのいずれとも競合・誤打をきたさない導線を徹底維持する。

## 2. 実装およびテスト戦略（Dex & CCへの手引き）

### (1) `isStampNoOp()` をはじめとする既存ロジック・テストの刷新
- これまで、同一スタンプを打刻した場合を「何も変化を起こさない (no-op) ・履歴も追加しない」ものとして処理・判定していた関数（`isStampNoOp()` やこれに関連する既存イベント分岐）が存在する。
- CCの実装フェーズにおいて、これらを削除・改名・拡張し、**`applyStampOrToggleClear()` など、同値判定時は明確に初期空欄オブジェクトを構築して歴史へ刻むロジックへと昇華** すること。
- これに伴い、**`frontend/src/App.cycle12.test.jsx` および `cycle12Utils.test.jsx` 内の既存テスト（旧 NoOp 仕様前提のケース）を直ちに洗い出し、今回のトグル・空欄復元仕様に準拠するようアサーションを更新・進化させる** こと。

### (2) 回帰テスト・強化ケースの必須追加
`App.cycle12.test.jsx` または `cycle12Utils.test.jsx` （ないしは `cycle13` テスト suite）に、以下のテストケースを恒久財産として必ず追加・PASS証明すること。
1. **トグル消去の初期化確認**: 同一スタンプを押した際、`shift` のみならず `isFixed`, `hours`, `note`, `isError` のすべてが初期状態へ確実に抹消されていることの検証。
2. **希望休消去時の連動検証**: 「休」セルの重ね打ち消去完了直後、`employees[].requests` から該当する日取りが正確に削除・再計算 (`buildRequestsFromMatrix`) されていることの確認。
3. **歴史原子性（Undo/Redo）検証**: 消去操作で履歴が1つ増え、Undo を呼べば元の詳細属性を備えたセルが蘇る旨のシームレス・テスト。
4. **許可シフト外でも消去可能な特例テスト**: 対象シフトが許可シフト一覧に含まれない状態であっても、既存の同値セルへはトグル消去が有効機能する証跡。
5. **PCおよびスマホの生成ボタン表示導線**: プライマリとして「空欄自動作成」が表示され、「再最適化」が上級メニュー・コンファーム経由で到達可能となっているDOM構造・表示検証。

## 3. バージョン管理・品質ゲート運用規則

- **Air (P1) フェーズにおけるバージョン取扱**:
  - 本作業（P1 Blueprint 策定）では製品コード（`App.jsx` など）を変更しないため、画面および `CURRENT_STATUS.md` の表記バージョンは現行の **`v4.47` を保持（変更なし）** とする。
- **CC (P3) 実装段階の採番規定 (Version Gate)**:
  - 未実装の段階から未来のバージョンを固定予言・決め打ちすることは決して行わない。
  - CC が製品実装（`App.jsx` および対応モジュール）を開始するまさにその時点での**最新の `main` のバージョン番号を取得し、そこから確実に `+1` した連番へ PC / スマホ 2か所および `CURRENT_STATUS.md` を連動改訂** すること。
  - 実装後のコミット前には `node scripts/check_version_gate.mjs`, `git diff --check`, `git status --short` を100%パスさせること！
